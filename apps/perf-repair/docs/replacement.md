# Replacement

From an app's source to a compiled and interop-checked replacement of each call site the model chose to replace; nothing is measured after a recommendation. Types: `src/perfrepair/dto/site.py`, `src/perfrepair/dto/dossier.py`, `src/perfrepair/dto/replacement.py`.

## Flow

| step | who | reads | writes |
|---|---|---|---|
| detect | static | app root; engine types from the packaged names catalog; the run's probe and providers to resolve each site | `<app>/sites.json` |
| scope | static | sites, app source, `scope/engines.yaml` | `<app>/scopes.json` (schema 5; `Scope` per site: function span, sinks, key source, `lifecycle`, `pattern`) |
| units | static | scopes, app source, `scope/units/relations.yaml` | `<app>/units.json` (`Unit`: members, `Link`s with lines on both sides, the units it shares a function with) |
| dossier | static | scopes, units, app.json `targetSdk`, `grouping/groups.json` (with its `interop` section), `grouping/screen.json`, `measurements.json` | `<app>/dossiers.json` (schema 7, the rows of the scope's `pattern` variant only and its current item's `perCall`, `perfMode` the selection, estimates of its metrics only; `Dossier`: function source, current item, `Option`s with interop status and `Estimate`s; `units`: the units asked, each with `stays`, its members without options, and `pairs`, the interop of every two differing items a replace can leave an inverse link's sides on: an option of a member with options, the current item of one that stays) |
| upgrade | list, else model | one broken use's `upgrades` row, no source | `<app>/upgrade/` outbox, `upgrades.json` ([upgrade.md](upgrade.md)) |
| replace | model | one unit, the `Dossier` of each member with options and the members that stay, per conversation | `<app>/replace/` outbox, `replacements.json` (`Replacement`) |
| edit | static | replacements, units, app source | `<app>/patched/` (a copy; the app is never edited), `edits.json` |
| harness | static | scopes, dossiers, the original and patched function, the results' `effective.yaml` | `<app>/harness.yaml` for cryptobenchmark; inputs with their source (`docs/repair.md`) |
| check | device | `harness.yaml` | `<app>/measured/scoped/scoped-plan.yaml`: compile and interop per scope |
| report | static | every file above (`units.json` required) | `<app>/report.json`, `report.md`; `summary.json`, `summary.md` across apps |

## Guide

```
python3 -m perfrepair guide --app <root> --device-results <device> \
    [--perf-mode generic|<keys>] [--agent ...] [--auth ...] [--prompts DIR] [--limit N] [--refresh] [--device [--config <global.yaml>]]
python3 -m perfrepair guide --device-results <device> ...   # without --app: every apps.targets entry
```

- The lower-level command under `apps/cli/facade.py` ([facade.md](../../../docs/facade.md)); it needs `pip install -e apps/perf-repair` or `PYTHONPATH=apps/perf-repair/src`.
- `--max-change` defaults to `apps.maxChange` ([change-classes.md](change-classes.md)).
- `--perf-mode`, `--limit` and `--device` default to `apps.perfMode`, `apps.limit` and `apps.measure`, `--config` to `pipeline.py`'s lookup, `--harness-config` to `--config`, the model to the `apps.agent` role; `ai replace` uses the `apps.replace` role (`docs/settings.md`).
- `--refresh` asks again the replace decisions whose dossier changed, and, when the guide runs the device stage (no named folder), rebuilds `primitives.tsv`; without it such an app stops with `dossier_changed` (`docs/decisions.md` Site replace).
- `--run-id` names the run record, unset a new timestamp; `--on-existing` is `overwrite`, `resume` or `skip` ([artifacts.md](artifacts.md#run-record)).
- `--stop-after-device` ends after prerequisites: target detect, used set, benchmark, inbound; no model call. `--outcome FILE` writes `{device, run, exit, code}`; `--run-settings FILE` stores that JSON under `settings` in the record.
- `--device-results` is required unless `--results-root` is set.
- Named folder (`--device-results`, or `device.id`): it must already hold `manifest.yaml`, `rows.json`, `measurements.json` (inbound) and `grouping/items.json` (grouping build): device-level stages, made once per device, never per app; a missing one stops with `missing_device_stage`; no benchmark runs; the grouping step asks the items with no decision.
- `--results-root` alone: prerequisites calls probe_device() on that root (`docs/pipeline.md` Device stage; on the phone with `--device`), printing `device <stage>: reused` or `ran: <reason>`; the grouping step asks what coverage finds missing (`docs/pipeline.md` Grouping knowledge) by `grouping assign` and `grouping report`, with the guide's `--agent` and `--perfrepair-config`, and prints `reused`, or what it ran.
- With `device.filterByApps` (default) prerequisites runs every target's app step on the probe before the device benchmark and writes `used.json`, so grouping and the benchmark cover only the targets' items ([used-set.md](used-set.md)); that app step is not run again.
- Steps in order: prerequisites, targets (`<device>/targets.yaml`, [targets.md](targets.md)), grouping, interop (`<device>/grouping/interop.yaml`, [grouping.md](grouping.md): on the benchmark's own target, so a device folder needs `--device`; else `interop_unverified` and the pairs stay `not_run`), app (detect and scope), dossier, upgrade, replace, edit, harness; with `--device`: device (`pipeline.py --device --harness <harness.yaml>`, an attached phone; it writes `measured/` beside the harness), then report. Without `--device` the guide ends at the harness and prints the device command.
- Each step prints `guide <step>: ok: <detail>`; the first failing step prints `guide <step>: stop <code>: <detail>`, and ends that app; a stop in prerequisites, grouping or interop ends the run, exit 1, no app runs.
- Over the apps: prerequisites, grouping and interop once, each app's steps, then `guide summary:` (`report summary` over every `<app>/report.json`; a dry run has none) and one line per app: `app <id>: ok`, `reused`, `stop <code> at <step>: <detail>`, or `not_run <why>`.
- One app's stop, gate rejection or bug (`stop bug at <step>`, the traceback in `log/bug.log`) is recorded and the next app runs. A provider failure (`claude_cli_failed`, `claude_api_failed`) stops the loop, the rest `not_run`, since every app would fail the same way.
- Exit 0 only if every app reached its last step, the harness or with `--device` the report, or was reused: `no_options` and `no_replacement` count against it on the run that reaches them; a later unchanged run reuses them, `reused (<code>)`.
- Ctrl-C ends the loop at the running app (`stop interrupted at <step>`); the summary, `apps-index.tsv` and its line are written, then it is raised again.
- Reuse is of `apps.targets` only; `run_dir/run_record.py` owns it ([artifacts.md](artifacts.md) Run record). An app is done when it reached its last step or a terminal stop (`no_options`, `no_replacement`) with no unit left unasked under `apps.limit`: `<app>/finished.json` holds the digests of its source and build files, its `scopes.json` and `units.json` as the run left them, the scoper version (a digest of perf-repair `app/`, `scope/`, `source/`, `result/`, `repair/`), the harness version (the host's digest of its code from `harness.yaml` to a measured harness, from `pipeline.py --identify`, read once per run before the apps), `groups.json`, `rows.json`, `measurements.json`, the screening catalog and the replace charter, its mode, whether it was measured and then the harness config's digest; the same on a later run means no step for it, `reused`. Any other stop, a bug, Ctrl-C or a cap that left units is not done; the first step of an app's rerun removes its `finished.json`, `report.json` and `report.md`, so a stop leaves none behind. `--app` and `--refresh` run every time; an unreadable `finished.json` is not done. A rerun repays nothing: its replace outbox resumes.

| stop code | step | when |
|---|---|---|
| `no_targets` | before prerequisites | no `apps.targets` entry resolves to an app ([targets.md](targets.md)) |
| `target_missing` | the target | an `apps.targets` path entry is no folder; its earlier results stay |
| `missing_results` | prerequisites | no `manifest.yaml` in the device folder |
| `missing_device_stage` | prerequisites, grouping | `rows.json` or `measurements.json` absent, `grouping/items.json` absent, or items with no decision in a named folder; the line names the commands |
| `app_failed` | app | `perfrepair.app` exits non-zero, or its gate refuses the folder, whose reason the line carries |
| `several_project_roots` | app | `--app` holds several project roots; pass one of them |
| `no_options` | dossier | no scope has an option; the line lists the `noOptions` reasons |
| `invariant_failed` | replace | before the replace call: a blocking invariant of the app's scopes or of a group its dossiers draw from ([invariants.md](invariants.md)) |
| `invariant_undecided` | replace | before the replace call: an undecided invariant, the source does not tell; a warning unless `stops.invariant_undecided: stop` |
| `no_replacement` | replace | every scope is kept |
| `dossier_changed` | replace | a decision was made on an earlier dossier; the line names the scopes; `guide --refresh` asks them again |
| `edit_invalid`, `no_edit_applied` | edit | edits.json fails its validator; every edit is rejected, with the reasons |
| `harness_invalid` | harness | harness.yaml fails its validator |
| `no_dossier` | harness | an applied edit's scope has no `dossiers.json` entry; nothing is written |
| `<step>_failed` | any | a validation failure, coded `ValueError`, missing file or failed pipeline run inside the step |

## Report

`python3 -m perfrepair.report app --device-results <device> --app <src> [--perf-mode generic|<keys>]`, then `python3 -m perfrepair.report summary --device-results <device>`. A step whose file is absent is `not_run`; `sites.json`, `scopes.json` and `units.json` are required.

| report.json row field | value |
|---|---|
| `unit`, `sharedFunction`, `stayed` | the scope's unit id; the other units with a member in its function, whose edits its patched function leaves out; the unit's members a static keep left on what they use while another member is replaced, [] otherwise |
| `inputs` | the scope's harness.yaml `inputs`: `inputSize`, `keySize`, `from` (`app` or `run`); null when the scope is not in the harness |
| `decision` | `replace`, `keep` or `not_run`; its reason; source `llm`, `fallback` or `static`; `stale` true when replacements.json lists the scope as decided on an earlier dossier, marked in report.md |
| `edit` | `applied`, `rejected` (edits.json reason), `skipped` (not a replace), `not_run` |
| `compile` | `compiled`; `primitive_only` with the scoped-plan reason (`not_compilable`); `not_measurable` with its reason (`no_operation`: a factory, never generated); `skipped`; `not_run` (no device run) |
| `interop` | `passed`, `unchecked`, `not_comparable` (an identity-only output), `interop_failed`, `call_failed`, with the check and reason; `skipped`, `not_run` |
| `primitive` | the chosen option's dossier estimates: the benchmark's evidence, measured before the recommendation |

- `maxChange`, `recommendations` (each candidate above it: `scope`, `item`, `change`, `diff`) and `rejected` (a count per reason), summed per class and reason in summary.json; a recommendation is never applied.
- `brokenUses`: `counts` per status and `rows`, each broken use and what it became ([upgrade.md](upgrade.md)), a section of report.md; summed in summary.json `brokenUses`.
- One row per scope stays; `funnel` adds `units` (all of them) and `unitsReplace` (those replaced).
- `funnel`: sites → scopes → units → withOptions → replace → unitsReplace → applied → compiled → interopPassed.
- A scoped-plan.yaml whose scopes are not harness.yaml's is `measured_mismatch`.
- report.json names the app's project (Gradle `rootProject.name`, else its folder) and source path beside its id; a row carries the scope's `pattern` and `patternReason` and the model's `deciding` and `accepted`.
- summary.json: `modes` and `named` per app, the funnel summed and per app, `patterns` (`all` and `byApp`: `fixed`, `notFixed`, `unknownDefault` counts).

## Contracts

- A scope's `lifecycle` (`dto/lifecycle.py`) is evidence beside the function span, never a narrower region: `start`, `end` stay the function's bounds for edit, render and harness. `status` is `bounded` (one method creates, configures and uses the object; no escape, consumer or deferred lambda), `partially_bounded` with its reasons (`field`, `escape`, `wrapper`, `deferred`, `depth1`, `budget`, `configuration_not_found`, `use_not_found`), `no_real_use` (created and never used, nothing escapes), or `unsupported` (`parser_missing`, `engine_unknown`, `call_not_found`). `steps` are the calls on the object, each with role (`configure`, `use`, `consume`, `other`), line and `where` (`same` or `depth1`, one method away in the class); `requirements` name each value a step takes (`key`, `parameters`, `input`) and its origin in a closed list (`parameter`, `field`, `same_class_call`, `other_call`, `generated`, `derived`, `keystore`, `decoded`, `storage`, `literal`, `unknown`) with its line; `operations` are the benchmark operations the steps perform, empty when unknown. The validator refuses a value outside the lists or a cited line outside the file.
- A scope's `pattern` is its divergence category, `fixed` (the setup the API lets a caller keep is kept) or `notFixed` (the setup runs on every call), by a fixed rule over its lifecycle (`scope/pattern.py`); `patternReason` names the rule and `patternLines` the site, configure and use lines it read. The validator recomputes it.

| patternReason | pattern | lifecycle |
|---|---|---|
| `created_per_call` | `notFixed` | binding `local` or `chain`, `bounded` or partial only by `wrapper`, `depth1`; a use found |
| `held_in_field` | `fixed` | binding `field`, partial only by `field`, `depth1`; every use one method away |
| `unknown_default` | `notFixed` | anything else: an escape, a return, a deferred use, a cut budget, a step not found, a field used beside its creation, `no_real_use`, `unsupported` |

- A requirement is open when its origin is in `OPEN_ORIGINS` (`parameter`, `field`, `same_class_call`, `other_call`, `unknown`) and no single closed origin one method away settles it. Code reads on from it in the outermost class of its file: field writes, call arguments in the class, returned values, a branch's operands (never a join's, an array's size or an index), then on from each open one. At most `REACH_METHODS` methods, `REACH_HOPS` hops, `REACH_LINES` values per requirement; past any the requirement stays open, never a wider reading.
- Settlement: when every path closes to one origin, with no path open or cut and no parameter or field other classes can reach, the requirement holds `settled: {origin, line}` and nothing asks.
- Scoping is local and has no cross-file analysis: a requirement from elsewhere (`parameter`, `other_call`, with its line) is a recorded fact, and unknown is an allowed result. A model role choosing among the in-class lines was tried and removed: on a real app it changed no `keySource` and 12 of 25 answers were wrong.
- `origin` on a requirement is what code read and is never rewritten; `status` and `reasons` stay as code read them.
- `keySource` takes a settled key origin only when it is in `KEY_SOURCES` and the view is `unknown` or `parameter`, so a closed reading stays. The `DERIVED_RISKS` rows read `keySource`, so they follow it; `storage`, `unknown` and `parameter` imply `key_compatibility` too. Site-replace shows each settled requirement as `settled: <origin>, line <n>`.
- `keySource` is the key requirement's origin when it is one of `KEY_SOURCES` (a field's or a private method's parameter's single origin one method away when there is one), else the pattern match; `sinks` stay the pattern match.
- An `energyJ` estimate carries `kind`; `estimated` also shows in its `configuration`. A metric both sides have with no ratio is in the option's `noEstimates` with its reason: `energy_kinds_differ` (sides of different kinds), `zero_median` (the current median is 0), `too_few_runs` (a side below `MIN_RUNS`, the gate's `low_quality`); the replace message shows each as `no estimate: <metric> at <configuration>: <reason>`. A `benchmark.json` without a kind reads as `measured`.
- An option's estimates cover only the configurations of the lifecycle's `operations` when it knows them; its pins come from every operation, since parameters do not depend on it.

- The app gate finds the outermost Android project roots under `--app`, down to 4 levels: a folder with `settings.gradle(.kts)`, with `build.gradle(.kts)` beside an Android source set (at `--app` itself, any build file), or a legacy Ant project (`AndroidManifest.xml` beside `project.properties`, scanned like any other); the folders of `app/find/ignored.yaml` are skipped (tooling, and stale source copies such as `NONE_TRANSFORMED_`, counted as `skippedCopies` on `app detect`) and symlinks are not followed. One root is `<path id>`; several become units `<path id>.<root dirs joined by '.'>`. `app.json` `projectRoot` is the root relative to `--app`, and site files are relative to it, so a later `--app`, that project root, reads them.
- A unit is the objects decided and swapped together: the connected components of the links; a scope with none is a unit of one. Only `bounded` and `partially_bounded` scopes link: an object never used or never read has nothing to keep in step. Its `id` is `unit_id(app, members)`. (A multi-root app's `<path id>.<root>` folders are another thing, one per project root.)
- A link names its lines on both sides, and they come from that side's lifecycle. `shared_key`: two key requirements with one origin and one line (a field, a parameter both steps name, one call), never `unknown` or `literal`. `producer_consumer`: an output of a `producers` call (`relations.yaml`) reaching a key requirement: `line`, the requirement's origin is that very line; in one outermost class, `call` (the line calls the producer's function, which returns), `field` (the output is written to the field the requirement reads) or `parameter` (the parameter the step names has the type the producer's method returns, and the names' first segments agree when both are known). `inverse`: one engine type, one algorithm, operations inverse in `relations.yaml`, and `key` or `input` (one origin and one line), `producer` (one producer feeds both) or `parameter` (both take their key from their caller, in one class: the same contract, though no caller is seen; the weakest evidence, kept because it pairs a wrapper's encrypt and decrypt).
- A scope's `id` is `scope_id(app, file, function, line, call)`, so rerunning detection and scoping on the same source gives the same ids, and every later step refers to a scope only by id.
- An `Option` is a candidate up to `maxChange`: a member of the site's group available in the app's process (from the platform or bundled by the app), or a candidate of [change-classes.md](change-classes.md). Its `pins` are the parameters that make the swap like-for-like (IV length, tag length, OAEP digests); `null` means unknown (no configuration measured on both sides), and the gate refuses a `replace` to it. A benchmark row without `parameters` is the coded error `missing_parameters`.
- An `Option`'s `interop` is `pair_status(groups, current, item)`: `pass`, `not_checkable`, `not_planned` or `not_run`; required, no default. A pair whose interop check failed is never an option; a scope that loses every option that way is in `noOptions` with `interop_failed`. A groups.json without an `interop` section is refused. The validator refuses a status outside that set, `fail`, or one that differs from groups.json.
- An `Option`'s `screen` is the item's status for this app ([screening.md](screening.md) Use): screen.json's verdict, raised to `platform_deprecated` by `ScreeningHandler.for_app` at app.json's `targetSdk`; null without screen.json. A `broken` item is never an option, not even the same algorithm from another provider. A `platform_deprecated` item is one only as the current item's canonical name and key size, at no worse a status than the current's; a scope that loses every option that way is in `noOptions` with `deprecated_only`. The validator recomputes the app's statuses with the handler and refuses a `screen` that differs or an option refused as a target.
- A broken current is not asked by replace: its scope is in `noOptions` as `broken_use` and in `upgrades`, as `person_judges: <reasons>` when each accepted, measured member is refused, or as `no_secure_option` when the family has no such member. Its candidates are the family's accepted items no reject reason of [change-classes.md](change-classes.md) refuses, up to any class whatever `apps.maxChange`, narrowed to `catalog/upgrades.yaml`'s targets when any is measured (the others `not_listed` in `notOffered`), best first by the option's own median at the site in the mode's metrics, a harness-only provider last; `no_gain` never applies. A broken use `no_real_use`, `variant_not_measured` or the like is in `brokenUnreached` with that reason.
- A `replace` to an option whose `interop` is not `pass` must declare `unverified_interop` (a `DERIVED_RISKS` row on the option, like the scope rows).
- An `Estimate` is graded, never a gate: `pImprove` is the probability the option is better on that metric. Below 0.95 the report says `warn` with the number; it is `null` when either side has fewer than two runs, rendered `n/a (n<2)`.
- A site whose algorithm name providers disagree on resolves `name_conflict` and reaches `noOptions` as `unresolved`; it never stops the app step.
- `noOptions` reasons are `NO_OPTION_REASONS`, in filter order, the first filter that leaves nothing named: `no_real_use`, `not_on_device`, `unresolved`, `variant_not_measured`, `not_grouped`, `no_alternative`, `none_available`, `deprecated_only`, `interop_failed`, `no_gain`, `broken_use`, `no_secure_option`, `person_judges`, `provider_held_key` (last, per unit: this member has options, but a member of its unit uses an item whose key contract is `provider_held`; that key cannot move to another provider, so no member is swapped; a `keystore` key source alone stays a declared `key_compatibility` risk). `variant_not_measured`: the current item has rows only in the other benchmark variant (a key generation is measured `fixed` only), and a scope never takes the other variant's numbers. `no_real_use` comes first: the lifecycle shows the object is never used, so no device or app change makes it worth measuring; then `not_on_device`: the site's provider or name is not on the device, so the fix is the device stage (`providers.bundled`), not the app; `deprecated_only` sits after `none_available` (a target that cannot run says so, whatever its status) and before `interop_failed` (a pair never offered needs no interop result). A scope in `noOptions` is never asked: `replacements.json` holds a static `keep` for it whose reason is its code, so it covers every scope.
- A member with no option stays on what it uses (its static keep), and the unit's other members can still be replaced: a group's members share the input, key and output contract, so a provider swap of one side still meets the other, and the interop check is what proves it. Whole-unit swaps become a requirement only once output bytes change. An inverse pair left on two items needs their interop (`pass`); `fail` refuses the answer, anything else needs `unverified_interop` on each swapped side. The row of every member of such a unit says which members stayed (`stayed`).
- The model picks, per unit, one option for every member with options or `keep` for all of them, and expresses the change only as `Edit`s of a kind in `EDIT_KINDS`. Static code renders and applies them. A replacement whose edits do not apply (`edit: rejected`), do not compile in the harness (`compile: primitive_only`), or fail the interop check (`interop: interop_failed`; data from before the swap must still decrypt after it) is reported with the reason, and is never measured.
- `harness.yaml` names each scope's original and patched function source, its inputs, and its `current` and `option` items. Inputs are the app's static sizes (`from: app`), else the largest sizes the run configured for both items (`from: run`); a parameter type the harness cannot build stays `unsupported_parameter`, never a made-up value. cryptobenchmark compiles both into the benchmark app and measures them like any other case.
